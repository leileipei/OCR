# Umi-OCR 多人 Web 系统设计

日期：2026-07-13  
状态：已确认  
目标环境：公司内网、Windows Server、e-cology 10、10–100 名用户

## 1. 背景与目标

将 Umi-OCR 从单用户 QML 桌面应用改造成公司内部多人 Web 系统。首期支持：

- 图片上传与批量 OCR；
- PDF/扫描件识别；
- 生成文本、结构化结果和可搜索 PDF；
- e-cology 10 单点登录；
- 部门与项目归档；
- 角色权限、完整审计和可配置保留期限；
- 每天少于 1,000 页、同时 1–5 人提交任务的负载。

首期不包括截图 OCR、二维码、OA 流程内发起 OCR、结果回写 OA、互联网开放、多租户计费或 GPU 调度。

## 2. 现有能力与改造边界

### 2.1 保留和迁移

- OCR 插件协议及 PaddleOCR-json、RapidOCR-json 等现有引擎；
- TBPU 文本块后处理，包括多栏、单栏、自然段、代码缩进和忽略区域；
- 图片识别、PDF 页面提取及可搜索 PDF 合成逻辑；
- OCR 参数、语言和输出格式的业务定义。

### 2.2 替换和重构

- 用 Vue Web 界面替换 QML 界面；
- 用正式 Web API 替换面向桌面进程的 Connector；
- 将全局单例任务管理器改成持久化任务队列和独立 Worker；
- 不把 Umi-OCR 现有 Bottle/WSGI 服务直接开放给多人使用；
- 将用户、项目、权限、审计、文件保留和运维能力作为新系统模块实现。

## 3. 方案选择

采用“模块化单体 Web 后端 + 独立 OCR Worker”。首期部署在一台 Windows Server，Web、调度、数据库和 OCR Worker 分进程运行。

不采用以下方案：

- 薄 Web 代理：仍受现有单例、弱并发、无鉴权和桌面进程生命周期限制；
- 完整微服务：当前负载不需要，其开发和运维成本明显过高。

当业务增长时，只增加 OCR Worker 或新增 Windows OCR 节点，Web API、权限模型和数据结构保持不变。

## 4. 总体架构

```text
员工浏览器
    │ HTTPS
    ├──────────── e-cology 10 单点登录
    │
IIS 反向代理
    │
Vue 3 前端 + FastAPI Web 服务
    ├── E10AuthAdapter
    ├── 用户/部门/项目/权限
    ├── 任务与文件 API
    ├── 审计与保留策略
    └── 调度服务
             │ PostgreSQL 任务队列
        ┌────┴────┐
   OCR Worker 1  OCR Worker 2
        └────┬────┘
        OCR 插件 / TBPU / PDF 合成
             │
   PostgreSQL + NTFS/企业 NAS
```

### 4.1 推荐技术选型

- 前端：Vue 3、TypeScript；
- 外部入口：IIS、HTTPS；
- Web 后端：FastAPI、Python 3.12 独立运行时；
- OCR Worker：与选定 Umi-OCR 插件兼容的隔离 Python 运行时；首期允许沿用现有 Windows OCR 运行环境；
- 数据库：PostgreSQL 16 或更高兼容版本，不引入 Redis；
- 文件存储：服务器 NTFS 独立数据盘或企业 NAS；
- 进程托管：Windows Service，开机启动、异常自动重启；
- 日志：结构化日志，以请求 ID 和任务 ID 串联。

Web 后端和 OCR Worker 不共享 Python 虚拟环境。这样可避免现有 Python 3.8/PySide2 依赖限制 Web 后端升级。

首期服务器基线建议为 Windows Server 2022 x64、8 个 CPU 核心、32 GB 内存，以及独立系统盘和数据盘。第 0 阶段根据 100 页代表性样本实测结果调整 CPU、内存和 Worker 数量。

## 5. 组件职责

### 5.1 Web 前端

- 从 e-cology 10 入口或系统地址进入；
- 上传图片/PDF，选择 OCR 语言、排版和输出选项；
- 展示队列位置、页级进度、错误信息和任务时间线；
- 浏览本人或项目任务，预览及下载结果；
- 提供项目成员、保留策略和管理员页面。

刷新页面、关闭浏览器或退出登录不会中断后台任务。

### 5.2 Web API

- 验证 E10 登录凭据并建立本地会话；
- 执行对象级权限检查；
- 接收分片上传，校验文件并创建任务；
- 查询状态、取消任务、下载结果；
- 管理部门、项目、成员、角色和保留策略；
- 记录审计事件。

### 5.3 调度服务

- 使用 PostgreSQL 行锁安全领取任务；
- 采用按用户轮转的公平调度，避免单一用户占满队列；
- 管理 Worker 租约、心跳、超时、重试和取消；
- 执行到期标记、待清理区和物理删除；
- 首期默认运行两个 OCR Worker，每个 Worker 同时处理一个文件。

### 5.4 OCR Worker

- 从任务中读取不可变的输入和 OCR 参数快照；
- 调用 OCR 插件识别图片或 PDF 页面；
- 执行 TBPU 排版处理；
- 按页写入进度与中间结果；
- 生成文本、JSON 和可搜索 PDF；
- 在临时目录完成输出，通过原子重命名发布完整结果。

Worker 不处理用户会话和权限；它只能访问已分配任务所需的文件。

### 5.5 文件存储

- 数据库只保存元数据，不保存大文件或 OCR 正文；
- 文件目录以随机对象 ID 组织，不使用用户提供的路径或原文件名；
- 输入、临时文件和结果文件使用不同目录和访问权限；
- 所有下载通过 Web API 鉴权，不提供永久公开 URL。

## 6. e-cology 10 身份集成

系统以 e-cology 10 为直接登录入口和身份来源。AD 继续作为公司现有企业目录，不由 OCR 系统重复认证。

`E10AuthAdapter` 对业务层提供统一结果：

```text
external_user_id
employee_number
display_name
department_id
department_name
account_status
session_expiry
```

首次登录创建本地用户映射，后续登录更新姓名、部门和账号状态。本地不保存 OA/AD 密码。

泛微公开资料确认 E10 提供统一身份管控、集成平台及 API/SDK 扩展能力，但客户实例启用的 SSO 方式取决于授权模块和部署配置。实施第 0 阶段必须由 OA 管理员提供当前实例的官方 SSO 接口文档、测试环境和测试账号；适配器按该官方接口实现，不采用网页抓取、共享 Cookie 或数据库直连等非官方方式。

保留两个本地应急管理员账号，仅允许从管理网段使用，并启用高强度密码。应急账号不能绕过文件访问审计。

## 7. 权限模型

### 7.1 系统角色

- 系统管理员：系统配置、外部用户映射、Worker 状态、保留策略上限和全部审计。默认无权直接查看业务文件正文；临时授权必须被审计。
- 部门管理员：管理本部门项目及成员，查看部门用量与任务状态。是否可查看文件由项目成员权限决定。
- 项目负责人：管理项目成员、项目任务、归档和保留期限。
- 普通用户：创建个人任务或被授权项目任务，访问本人及项目授权范围内的数据。

### 7.2 项目成员角色

- 查看者：查看任务状态与结果、下载文件；不能上传、删除或管理成员。
- 贡献者：拥有查看者权限，可提交项目任务；只能删除本人创建且尚未归档的任务。
- 项目负责人：管理成员、全部项目任务和项目保留策略。

每个任务同时保存创建人、所属部门和可选项目。权限检查在任务查询、预览、下载、取消、删除和共享时分别执行，不能只依赖前端隐藏按钮。

## 8. 数据模型

核心实体包括：

- `users`：本地用户与 E10 外部身份映射；
- `departments`：部门快照及外部部门 ID；
- `projects`：项目、部门归属、状态和保留策略；
- `project_members`：用户、项目和成员角色；
- `ocr_jobs`：任务状态、参数快照、进度、重试次数、租约和归属；
- `job_files`：输入/输出对象、哈希、大小、页数、媒体类型和存储位置；
- `job_events`：用户可见的任务时间线；
- `audit_events`：安全审计事件；
- `retention_holds`：合规保留记录；
- `worker_heartbeats`：Worker 状态与当前任务。

审计事件包含操作者、动作、对象类型、对象 ID、时间、来源 IP、结果及必要的变更摘要。审计表不保存完整 OCR 正文。

## 9. 任务状态与数据流

任务正常状态：

```text
UPLOADING → QUEUED → RUNNING → PACKAGING → SUCCEEDED
```

旁路终态：

```text
FAILED | CANCELED | EXPIRED
```

处理流程：

1. 文件分片写入临时区并计算 SHA-256；
2. 校验真实文件格式、大小和 PDF 页数；
3. Windows Defender 扫描通过后，原子移动到输入区；
4. 在同一数据库事务中创建文件元数据和排队任务；
5. Worker 通过事务锁领取任务并建立有期限的租约；
6. 逐页识别并持久化进度；
7. 合成结果，在临时目录校验完成后原子发布；
8. 写入成功状态、结果元数据和审计事件。

同一用户连续提交大量任务时，调度器按用户轮转。管理员可配置单文件大小、PDF 最大页数、个人待处理任务数和部门用量限额。

首期默认限额为：单文件 200 MB、单个 PDF 500 页、每名用户最多 20 个未完成任务。管理员可以下调或上调，但上调前必须通过对应规模的资源测试。

## 10. 错误处理与恢复

### 10.1 Worker 崩溃

Worker 周期性续租。租约过期后，调度器回收任务并重新排队。中间文件不视为正式结果，避免重复发布和半成品下载。

### 10.2 重试

- 引擎无响应、临时 IO 或短暂数据库错误：最多自动重试两次，指数退避；
- 损坏文件、不支持格式、加密 PDF 或参数无效：立即失败；
- 每次尝试单独记录错误类别、摘要和耗时。

### 10.3 取消

- `QUEUED` 任务立即取消；
- `RUNNING` 任务设置取消标志，在当前页面完成后安全停止；
- 取消后清理临时文件，不发布不完整结果。

### 10.4 服务器重启

Windows 服务自动启动。调度器扫描过期租约并恢复未完成任务；已经原子发布且数据库尚未更新的结果通过一致性检查完成对账。

## 11. 保留与归档

- 系统管理员设置允许的保留期限范围；
- 项目负责人在范围内设置项目期限；
- 到期任务进入 30 天待清理区，期间项目负责人可恢复；
- 30 天后物理删除输入文件、结果文件和 OCR 正文；
- 被设置合规保留的任务跳过自动删除，解除后重新计算期限；
- 物理删除后长期保留任务 ID、哈希、操作者、时间和删除原因等最小审计信息。

个人非项目任务使用系统默认保留策略。

首期系统默认保留期为 180 天，项目可选范围为 30–3,650 天；待清理期固定为 30 天。合规制度另有要求时，由系统管理员调整范围并记录审计。

## 12. 安全设计

### 12.1 网络与会话

- 系统仅开放在公司内网；
- IIS 强制 HTTPS 和安全响应头；
- OCR Worker、PostgreSQL 和文件共享端口不对用户网段开放；
- 会话 Cookie 设置 `HttpOnly`、`Secure` 和合适的 `SameSite`；
- 所有有副作用的请求验证 CSRF；
- 登录、上传、下载和管理操作实施用户/IP 级限流。

### 12.2 文件

- 根据文件签名判断类型，不信任扩展名或浏览器 MIME；
- 只接受白名单图片格式和 PDF；
- 文件进入正式存储前由 Windows Defender 扫描；
- 文件名只作为转义后的展示元数据；
- 预览和下载每次重新进行对象级权限检查。

### 12.3 凭据与服务账号

- Web、Worker、数据库备份使用独立服务账号；
- 服务账号采用最小目录和数据库权限；
- 数据库及 E10 集成凭据由 Windows DPAPI 或企业凭据系统保护；
- 不将密钥写入仓库、普通配置文件或日志。

### 12.4 审计

上传、识别、预览、下载、共享、删除、登录、角色变化、保留策略变化和应急管理员操作均写入审计。普通管理员没有修改或删除审计记录的权限。

## 13. 运维、监控与备份

运维指标：

- Web、调度器、Worker、PostgreSQL 和存储健康；
- Worker 心跳和模型进程内存；
- 队列长度、最长等待、成功率、失败率和重试率；
- CPU、内存、磁盘剩余空间；
- 备份与清理任务结果。

触发告警的情况包括 Worker 离线、磁盘不足、队列持续积压、连续任务失败、数据库不可用和备份失败。结构化应用日志默认保留 90 天。

备份策略：

- PostgreSQL 每日备份；
- 文件存储每日增量备份或 NAS 快照；
- 每月在隔离环境执行恢复验证；
- 首期恢复目标为 RPO 不超过 24 小时、RTO 不超过 4 小时。

## 14. 测试设计

### 14.1 单元测试

- 权限矩阵和对象级授权；
- 任务状态机、租约、重试和取消；
- 保留策略和合规保留；
- 文件格式与路径安全；
- TBPU 文本后处理。

### 14.2 集成测试

- E10 测试账号登录、退出、会话过期和禁用账号；
- 图片与 PDF 识别；
- 多语言、排版选项和忽略区域；
- 可搜索 PDF 的文本层与页面对齐；
- 数据库与文件存储一致性。

### 14.3 故障恢复测试

- 识别中终止 Worker；
- Web、调度器及整机重启；
- 数据库短暂断连；
- 临时磁盘或结果盘不可用；
- 验证无任务丢失、无重复正式结果、无永久运行中任务。

### 14.4 安全测试

- 越权查询、预览、下载和删除；
- 路径穿越、伪造格式和异常 PDF；
- CSRF、会话固定、会话过期和限流；
- 审计完整性和应急管理员约束。

### 14.5 负载测试

模拟 5 名用户同时上传，两个 Worker 连续处理至少 1,000 页。验收标准：

- 无任务或文件丢失；
- 无重复正式结果；
- Web 查询、登录和下载在 OCR 满载时保持可响应；
- 任务公平调度生效；
- 资源使用不触发操作系统级内存不足。

## 15. 上线验收

上线必须同时满足：

- 单元、集成、恢复、安全和负载测试通过；
- 业务负责人抽查权限与审计符合预期；
- 数据库和文件恢复演练成功；
- E10 测试环境完成官方 SSO 接口联调；
- 连续试运行 5 个工作日无 P1/P2 故障；
- 运维人员已获得部署、备份、恢复、告警和应急账号操作手册。

## 16. 实施分期

### 第 0 阶段：技术验证

- 获取 E10 当前实例官方 SSO 文档及测试环境；
- 验证 OCR 引擎能在无桌面 QML 的 Windows 服务进程中稳定运行；
- 验证 PDF 提取和可搜索 PDF 合成模块可独立调用；
- 对 100 页代表性样本测量 CPU、内存和耗时，以确定 Worker 数量。

任一验证失败时先调整适配层，不进入完整业务开发。

### 第 1 阶段：最小业务闭环

- E10 登录、用户映射；
- 图片/PDF 上传；
- PostgreSQL 队列和两个 Worker；
- 任务进度、文本结果和可搜索 PDF 下载；
- 本人任务历史。

### 第 2 阶段：企业权限与治理

- 部门、项目和成员角色；
- 审计、保留策略、合规保留；
- 管理端、监控、告警和备份恢复。

### 第 3 阶段：试运行与上线

- 安全、故障和 1,000 页负载测试；
- 小范围部门试用；
- 修复问题后正式上线。

## 17. 外部依赖与约束

- OA 管理员提供 E10 官方 SSO 能力、文档、测试账号和测试环境；
- 基础设施团队提供 Windows Server、HTTPS 证书、PostgreSQL、数据盘/NAS、备份和告警渠道；
- 安全团队确认 Defender 扫描、服务账号、管理网段和日志保留策略；
- 业务团队提供不同语言、排版和 PDF 类型的脱敏验收样本；
- 使用的 OCR 插件、模型和第三方组件必须完成许可证核对和安全扫描。
